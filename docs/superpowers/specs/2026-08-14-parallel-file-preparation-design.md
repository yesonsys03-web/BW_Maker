# 파일 준비를 작업 프로세스로 병렬화

2026-08-14. 사용자 요청: *"폴더 하나에 100장이 넘을 때도 있어. 지금 구조는 100장을
한 장씩 처리하잖아. 캐시는 멀티 워커로 작성하는데."*

관찰이 맞다. 폴더를 로드한 뒤 사용자가 기다리는 두 패스는 작업 프로세스를 **한 개도**
쓰지 않는다. 파일 패널에서 작업 프로세스를 6개로 올려놔도 그 둘은 메인 엔진 하나가
직렬로 돈다.

## 1. 무엇이 문제인가

폴더를 로드하면 순차 패스가 둘 돈다.

| 화면에 뜨는 말 | 위치 | 파일당 하는 일 |
|---|---|---|
| **"여는 중"** | `App.tsx:468` → `drainLoadQueue` | `open_psd`(트리·세션) → `apply_preset`(매칭·연산) |
| **"미리보기 준비 중"** | `App.tsx:1143` → `drainLoadQueue` | 미리보기 한 장 합성 → `PreviewCache`(프런트 RAM) |

둘 다 메인 엔진 프로세스 하나가 stdin 큐로 직렬 처리한다. 그리고 그렇게 만든 이유가
코드에 적혀 있다 — `src/lib/loadQueue.ts:19`:

> *"한 번에 하나씩 도는 데는 이유가 있다. 엔진은 stdin 큐를 순서대로 처리하므로
> 동시에 던져봐야 줄을 설 뿐이고, 파일 사이에서 한 번씩 양보해야 그 틈에 사람이 누른
> 미리보기 요청이 끼어들 수 있다."*

**이 전제는 작업 프로세스에서 성립하지 않는다.** 워커는 별도 프로세스라 메인 엔진의
stdin 큐에 줄을 서지 않는다. 순차여야 할 이유가 그 경로에서는 사라진다.

### 1.1 실측 — 어디에 시간이 가나

2026-08-11 납품 판 프로파일(`PSD_ENGINE_PERF`, 배포 경로 그대로):

    open_psd            2.5~6.6s   BG 판(1.5GB/748MB/520MB) 로컬
    잎 타일 디코드       0.7~50s    잎 하나당. 무마스크 59.9Mpx가 49.7s
    오버레이 계산        8.9~36s    뷰 하나당. CH #44는 뷰 15개 = 첫 렌더의 79%
    최종 합성 + PNG      0.04~0.37s 핫 기준. 전송·인코딩은 납품 판에서도 병목이 아니다

즉 파일당 비용의 거의 전부가 **파일 단위로 완전히 독립**이다. 파일 A의 트리를 만드는
일과 파일 B의 미리보기를 굽는 일 사이에 공유 상태가 없다.

**아직 안 잰 것 — 이게 이 트랙의 기준선이다.** "폴더 100장 로드 → 두 패스 완료"까지의
벽시계 시간을 잰 값이 없다. 위 표는 파일 하나 안의 분해다. 구현 전에 반드시 재고,
같은 방법으로 구현 후에 다시 잰다(9절). 이 프로젝트에서 실측 없이 세운 이론이 여러 번
틀렸다.

색 판(`_CO_`)은 SMB NAS에 있고 실측 한 장이 283MB·드로잉 레이어 144장이다. NAS 경유
오픈 시간은 안 쟀다 — 로컬 BG 판의 2.5~6.6s를 그대로 적용하지 말 것.

## 2. 무엇을 바꾸나

두 패스를 **하나의 "파일 준비"로 합치고, 파일 단위로 작업 프로세스에 나눈다.**

    지금:   [여는 중 100장 순차] → [미리보기 준비 100장 순차]     메인 엔진 1개
    바꾼 뒤: [파일 준비 100장 — 작업 프로세스 N개가 나눠 처리]

**설정은 안 바뀐다.** 작업 프로세스 개수는 파일 패널의 기존 드롭다운(1/2/4/6) 값을
그대로 쓴다. 새 설정을 만들지 않는다 — "작업 프로세스 개수"의 뜻이 하나로 유지되어야
한다.

**화면에서 바뀌는 것은 둘뿐이다:** 진행바 둘("여는 중"·"미리보기 준비 중")이 하나로
합쳐지고(7절), 전체 캐시 버튼에 대기 문구가 붙는다(6.3). 그 밖의 버튼·패널·동작은
그대로다.

**합치는 것이 핵심이다.** 지금은 여는 중에 PSD를 한 번 열고, 미리보기 준비에서 세션이
이미 밀려나 있으면(LRU 2칸이라 대개 그렇다) `withEvictedSessionRetry`가 **또 연다.**
작업 프로세스는 한 번 열어서 트리·프리셋 매칭·미리보기를 다 만들고 그 파일을 놓는다.

### 2.1 왜 작업 프로세스가 이 일을 할 수 있나

`apply_preset`은 세션에서 **트리와 경로만 읽는다**(`rpc.py:402`) — 픽셀도 PSD도 안
본다. 이미 같은 판단으로 `auto_merge_operations`·`auto_merge_preview`가 세션 대신
트리를 받도록 옮겨져 있다(`rpc.py:382`의 주석: *"이름만 보고 묶는 계산이라 픽셀도 PSD도
필요 없는데, 세션을 요구하면 그것이 축출됐을 때 700MB짜리 파일을 통째로 다시 읽어야
한다"*). 파일 준비는 그 선례를 따른다.

미리보기 쪽은 더 확실하다. 작업 프로세스는 **이미 이 일을 하고 있다** —
`warmworker.py:19`가 *"프리셋마다 갓 적용한 화면의 미리보기 PNG까지 디스크 캐시에 미리
굽는다"*고 명시한다. 전체 캐시가 몇 시간짜리인 것은 그 위에 타일 전량 + 뷰 오버레이
전량을 얹기 때문이지, 미리보기 한 장이 느려서가 아니다. 그 한 장만 떼어낸다.

## 3. 작업 프로세스 프로토콜 — 잡 하나 추가

기존 잡 둘(전체 캐시 워밍업 `{"path","presets"}`, 배치 내보내기 `{"path","export"}`)은
**그대로 둔다.** 세 번째를 더한다.

    보냄: {"path": "...", "prepare": {"preset": {...}, "maxSize": 1500}}

    받음: {"event": "file", "path": "...", "ok": true, "result": {
             "tree", "mtime", "width", "height", "colorMode", "depth",
                                              ← open_psd가 주던 것 (sessionId 제외)
             "matchedLayerIds", "skippedLayers", "operations",
                                              ← apply_preset이 주던 것
             "pngPath"                        ← 미리보기 준비가 만들던 것 (없을 수 있음)
           }}

미리보기를 **무슨 그림으로** 구울지는 이미 있는 `warmworker._preset_preview_args`를
그대로 쓴다. 전체 캐시가 지금 쓰는 바로 그 함수다.

**새 키 계산 코드를 만들지 않는 것이 이 설계의 규율이다.** `rpc.py:172`가 경고한다:

> *"프런트(previewCache.ts previewRenderSpec)가 보내는 값과 워커
> (warmworker._preset_preview_args)가 만드는 값이 이 함수 위에서 같은 키로 접혀야
> 워커가 구운 그림을 클릭이 찾는다 — 세 곳 중 하나를 바꾸면 나머지 둘을 같이 봐야
> 한다."*

네 번째 곳을 만들면 그 경고가 여섯 쌍으로 늘어난다. 파일 준비는 기존 셋 안에 머문다.

`_preset_preview_args`가 `None`을 돌려주는 두 경우(매칭 0장 / 매칭이 "파일을 연 직후
보이는 전부"와 같음)는 지금 프런트 규칙과 같다. 후자는 화면이
`render_document_preview`(PSD에 저장된 병합 이미지, 즉시)로 가므로 굽지 않고
`"documentView": true`만 실어 보낸다.

Rust(`warm.rs`)는 **안 고친다.** `warm_worker_send`는 payload를 그대로 전달만 하고,
그 이유가 주석에 있다(*"Rust가 필드를 알면 잡 종류가 늘 때마다 세 층이 같이 움직여야
한다"*). 새 잡은 Rust에 투명하다.

## 4. 프런트 — 모드 하나 추가

`src/lib/warmWorkers.ts`에 세 번째 모드 `runPrepareQueue`를 더한다. 큐 코어
(`runWorkerQueue`)는 **안 건드린다** — 그 파일이 못박아 뒀다:

> *"큐·끌어가기·실패 가시화(무소식 워치독, 전달 실패 한도, 시작 실패 처리)는
> runWorkerQueue 한 벌뿐이다 — v0.2.7의 침묵 멈춤을 소리 나게 만든 기계이므로, 잡
> 종류가 늘어도 여기서 갈라지면 안 된다."*

모드 추가가 정해진 확장 지점이다. 당겨 가기(빠른 프로세스가 더 가져감), 죽은 프로세스의
파일 재배정, 30초 무소식 워치독, 전달 실패 한도를 전부 물려받는다.

결과가 오면 프런트는 지금과 같은 액션을 dispatch한다(`openSuccess` / `applyPresetResult`
상당) — 리듀서와 화면은 결과가 메인 엔진에서 왔는지 작업 프로세스에서 왔는지 모른다.
`pngPath`는 `loadPngDataUrl`로 읽어 `PreviewCache`에 넣는다. 키는 **프런트가 지금처럼
`previewPlanFor(file)`로 계산한다** — 트리가 돌아온 뒤이므로 계산할 수 있다.

RAM 예산은 충분하다. 실제로 잰 미리보기 PNG가 **55KB와 87KB**였으므로(1500×659,
1500×623 — 표본 2장, `2026-08-10-project-file-design.md` 2.1절) 데이터 URL은 33% 커져
장당 ~73~116KB다. 100장이면 7~12MB로, `PREVIEW_CACHE_BUDGET_CHARS = 256MB`에 여유롭게
든다. **표본이 얇다** — 색이 많은 판은 더 클 수 있으니 상한으로 믿지 말 것. 넘치면
LRU가 도는 것이 지금과 같다.

## 5. 유일한 실질 위험 — `sessionId`

작업 프로세스는 세션을 만들 수 없다. 세션은 메인 엔진 `SessionStore`의 것이다. 그래서
**"트리는 있는데 `sessionId`가 없는 파일"이라는 상태가 새로 생긴다.**

**그런데 그 상태는 이미 존재한다.** 프로젝트 열기가 정확히 그것을 만든다 —
`App.tsx:758`:

> *"복원 직후의 항목에는 `sessionId`가 없다 — `restoreProject`가 `{ path, status,
> tree, mtime }`만 세우고 세션은 로드 큐가 나중에 채운다."*

그리고 같은 주석이 **키 계산도 이미 세션 없이 하고 있다**고 적어 뒀다: *"previewRenderSpec
자체는 sessionId를 쓰지 않으므로(가드는 previewPlanFor에만 있다) 여기서는 직접
계산한다."* 프로젝트 저장이 그렇게 한다.

세션이 이미 얼마나 덧없는지도 같은 방향이다. `SessionStore(max_sessions=2)`이므로 100장을
순서대로 열면 **98장의 `sessionId`는 이미 죽은 값**이고, 쓰는 순간
`unknown or evicted session`이 난다. 프런트는 `withEvictedSessionRetry`로 그때그때 다시
연다.

**그래서 이 작업은 새 상태를 발명하는 게 아니라, 이미 있는 상태(프로젝트 복원)를 두 번째
경로에도 허용하는 것이다.** 위험은 처음 판단보다 낮다. 다만 `f.sessionId !== undefined`를
보는 가드는 여전히 전수로 훑어야 한다(최소 `App.tsx:710`, `1258`, `1272`).

**방향은 하나다: `sessionId` 없는 "준비된 파일"을 정식 상태로 인정한다.** 세션이
필요한 호출부가 그 자리에서 연다 — `withEvictedSessionRetry`가 이미 하는 일과 같고,
"죽은 세션"과 "없는 세션"이 그 함수 안에서 한 갈래로 접힌다.

구현 계획에서 정할 것은 갈래가 아니라 **범위**다:

- `f.sessionId !== undefined`를 보는 가드 전수(최소 `App.tsx:1258`, `1272`). 각각
  "세션이 있어야 하는가"인지 "준비가 끝났는가"인지를 가려 후자는 새 조건으로 바꾼다.
  **두 뜻이 지금은 같아서 한 값으로 쓰이고 있다** — 이 작업이 그 둘을 가른다.
- 화면 표시: "아직 준비 중"과 "준비됐고 세션만 없음"이 사용자에게 구별되어야 하는가.
  후자는 클릭하면 즉시 그림이 뜨므로(RAM 캐시) 구별할 이유가 없을 수 있다.

**선택 사항(먼저 하지 않는다):** 준비가 끝난 뒤 메인 엔진이 활성 파일과 그다음 파일의
세션만 미리 채워두기. 세션이 2칸이라 그 둘이 전부이고, 지금 유휴 워밍업이 이미 같은
둘을 대상으로 한다(`App.tsx:1237`). 기준선 실측 뒤에 필요하면 얹는다.

## 6. 전체 캐시 · 배치 내보내기와의 관계

**두 기능의 코드는 안 건드린다**(사용자 결정). 단 6.1의 가드 한 줄은 예외다.

### 6.1 왜 동시에 못 도나

작업 프로세스 묶음이 하나뿐이고, 띄우는 함수가 기존 것을 **무조건 전부 죽인다**:

```rust
// src-tauri/src/warm.rs:59
pub fn warm_workers_start(...) {
    kill_all(&state);          // ← 먼저 다 죽이고 시작
```

묶음을 둘로 유지하면 동시 실행이 되지만 **메모리가 2배**다. 기록상 16GB 기계는 작업
프로세스 2개가 안전선이다(디코드 피크 실측 ~5GB/레이어). **기각한다.**

### 6.2 정해진 순서 규칙

| 지금 도는 것 | 새로 들어온 것 | 결과 |
|---|---|---|
| 파일 준비 | 전체 캐시 버튼 | **대기.** 준비가 끝나면 자동으로 이어서 시작 |
| 전체 캐시 | 파일 준비 재무장 | 파일 준비가 **작업 프로세스를 안 쓰고** 현행 메인 엔진 경로로 감 |
| 배치 내보내기 | 파일 준비 재무장 | 같음 — 현행 그대로 비켜섬 |

**대기를 고른 이유가 셋이다.** ① 사용자가 누르고 자리를 떠도 된다. ② 전체 캐시가
**더 빨라진다** — 파일 준비가 구운 미리보기가 디스크 캐시에 있어 전체 캐시의
`render_preview_cached`가 그 단계를 디스크 히트로 건너뛴다. 한 일이 안 버려진다.
③ 전체 캐시 진행바가 정확해진다 — 총량 추정이 트리를 아는 파일만 정확한데
(`App.tsx:1488`), 준비가 끝나면 전부 안다. `App.tsx:1471`에 *"프로젝트 로드 직후에는
대부분이 아직 안 열린 상태라, 그 순간 열린 몇 장만 쓸고 '완료' 팝업이 떴다"*는 과거
사고가 기록돼 있다.

**두 번째 줄이 필수인 이유:** 파일 준비 효과는 `state.opsByPath`가 deps라 아티스트가
눈을 하나 토글해도 다시 돈다. 그때 작업 프로세스를 띄우면 **몇 시간짜리 전체 캐시가
조용히 죽는다.** 전체 캐시가 어차피 같은 그림을 굽고 있으므로 비켜서는 쪽이 옳다 —
`App.tsx:1251`이 유휴 워밍업 체인에 이미 같은 판단을 적용해 뒀다.

**교착은 없다.** 파일 준비는 아무것도 기다리지 않고 메인 엔진 경로로 폴백한다. 그러면
작업 프로세스를 쥐고 있지 않으므로 전체 캐시가 시작할 수 있다.

### 6.3 건드리는 유일한 한 줄

전체 캐시 효과에 `if (preparing) return;`를 더하고 `preparing`을 deps에 넣는다. 준비가
끝나면 효과가 다시 돌아 스윕이 알아서 이어진다 — 바로 위에 있는
`if (batchRunning) return;`(`App.tsx:1470`)과 **정확히 같은 모양**이다. 버튼 문구에
"파일 준비가 끝나면 시작합니다"를 더한다.

## 7. 진행바 · 중지 · 실패

"여는 중"과 "미리보기 준비 중" 두 막대가 **하나로 합쳐진다.** 두 패스가 한 잡이 되므로
막대를 둘로 유지할 근거가 없다. 문구는 구현 때 정한다.

중지 버튼과 파일별 실패 카드는 지금 동작 그대로다 — 큐 코어가 이미 같은 규율을 갖고
있다(파일 하나의 실패가 큐를 안 끊고, 남은 파일은 `onAbandoned`로 사유째 적힌다).

**전체 캐시·배치 내보내기가 시작해서 작업 프로세스가 죽는 경우는 "실패"가 아니라
"취소"로 접어야 한다.** 접는 처리를 안 하면 남은 파일이 전부 실패로 적혀 *"미리보기를
미리 만들지 못한 파일 87개"* 같은 가짜 오류 카드가 뜬다. 6.2의 규칙이 이 경우를
대부분 없애지만, 경합은 남을 수 있으므로 접는 경로를 둔다.

## 8. 기각한 것

- **메인 엔진을 멀티스레드/멀티프로세스로.** 작업 프로세스라는 축이 이미 있고 검증됐다.
  새 축을 만들면 세션 2칸·GIL·psd-tools 스레드 안전성을 새로 다뤄야 한다.
- **작업 프로세스 묶음을 둘로 유지해 동시 실행.** 메모리 2배(6.1).
- **폴더 로드 시 전체 캐시를 자동 시작.** 2026-08-12에 사용자가 정한 UX를 뒤집는다
  (*"무조건 생성하는 게 아니라 사용자가 필요하면 생성"*).
- **파일 준비용 작업 프로세스 개수를 따로 두기.** 설정이 늘고 "작업 프로세스 개수"의
  뜻이 둘로 갈린다.
- **워커 소유권 중재자 파일(`workerPool.ts`).** 사용자 확인: 배치 내보내기는 미리보기
  준비가 전부 끝난 뒤에 하는 작업이라 시간이 안 겹친다. 6.2의 세 줄이면 충분하고, 세
  번째 사용자가 실제로 겹칠 때 다시 꺼낸다.

## 9. 검증

**기준선을 먼저 잰다.** 폴더 100장(또는 실제 작업 폴더) 로드 → 두 패스 완료까지의 벽시계
시간. 구현 후 작업 프로세스 1·2·4로 같은 방법으로 다시 잰다. 1절에서 적었듯 이 숫자가
지금 없다.

- 작업 프로세스가 구운 미리보기 키 == 프런트가 계산하는 키 — **통합 테스트로 못박는다.**
  3절의 "네 번째 곳을 만들지 않는다"가 지켜지는지를 이 테스트가 지킨다.
- 작업 프로세스 하나가 죽어도 남은 것이 그 파일을 이어받는가(큐 코어의 기존 규율).
- 전체 캐시를 누르면 대기했다가 이어서 시작하는가. 가짜 오류 카드가 안 뜨는가.
- 전체 캐시가 도는 중에 눈을 토글해도 스윕이 안 죽는가(6.2 두 번째 줄).
- 배치 내보내기 중에는 파일 준비가 작업 프로세스를 안 쓰는가(반쪽 PSD 방지).
- `sessionId` 가드 전수 확인(5절) — 파일을 클릭했을 때, 내보낼 때, 프로젝트를 저장할 때.

**앱에서 확인해야 한다.** 이건 지연 시간 변경이라 단위 테스트가 재지 않는다. 사용자가
`pnpm run tauri dev`로 직접 돌려 확인한다. 엔진 변경은 HMR로 안 오므로 재시작이 필요하다.
