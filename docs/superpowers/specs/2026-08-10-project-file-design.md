# 프로젝트 파일 — 껐다 켜도 그대로 뜨게

2026-08-10. 아티스트 요청: *"미리보기 작업하고 수동으로 모든 작업이 끝나고 프로그램
종료하면 해당 작업이 전부 초기화되잖아. 다시 오픈했을 때 기존 작업이 남아 있게 하는
방법 있어?"* 그리고 방식까지 본인이 짚었다: *"애프터이펙트 프로젝트 파일 열면 전부
그대로 뜨잖아."*

## 1. 무엇이 문제인가

앱을 끄면 파일별 작업이 **전부** 사라진다. `AppState`는 메모리에만 있고, 디스크에
남는 것은 프리셋 목록뿐이다.

사라지는 것이 둘이고, 둘 다 비싸다.

**손으로 한 판정** — `OpsState` 여섯 가지(체크, 눈, solo, 색 원본 지정, 라인 지정,
병합·이름변경 이력). 이름 규칙이 닿지 않는 판은 아티스트가 한 장씩 열어 지정해야
하는데(선화가 `TEMPLATE` 안의 `BORDER`인 판), 그 판단이 통째로 날아간다.

**만들어둔 그림** — 미리보기는 `PreviewCache`(메모리 LRU)에만 있다. 캐릭터 판 첫
렌더가 뷰당 수 초이고, 100장을 준비 큐가 채우는 데 오래 걸린다.

여는 비용도 있다. PSD 하나 여는 데 245레이어급이 3.4초라 100장이면 6분이고, 그
6분을 기다린 뒤에야 작업이 시작된다.

## 2. 무엇을 만드나 — `.bwproj` 폴더

```
내작업.bwproj/
  project.json      파일 목록 · 파일마다 경로·수정시각·트리·OpsState·매칭 결과 · 프리셋
  previews/
    <키해시>.png     저장 시점 화면의 미리보기 한 장씩
```

### 2.1 크기 — 재본 값, 그리고 표본이 얇다는 것

미리보기 PNG를 실제로 재보니 **55KB와 87KB**다(1500×659, 1500×623). 선화는 대부분
투명이라 잘 압축된다. **100장이면 6~9MB 정도**다.

**표본이 2장뿐이다.** 엔진이 렌더 디렉터리를 세대별로 지워서 그날 남아 있던 것이
그것뿐이었다. 색이 많은 판은 더 클 수 있으니 이 숫자를 상한으로 믿지 말 것.

(초안에는 "장당 1~3MB, 100장이면 100~300MB"라고 적혀 있었다. `previewCache.ts`
주석의 **base64 기준** 수치를 원본 PNG 크기로 잘못 옮긴 것이다. 폴더로 나눈 근거가
그 숫자였는데, 근거가 틀렸어도 결론은 아래 이유로 유지한다.)

### 2.2 그래도 폴더인 이유

크기 때문이 아니다. 셋이다.

- **필요한 것만 읽는다.** 열 때 화면에 뜨는 파일의 그림만 읽으면 되고, 나머지는
  스크롤할 때 읽는다.
- **표본이 얇다.** 색이 많은 판이 예상보다 크더라도 폴더는 그대로 견딘다. 한 파일에
  base64로 싣는 설계는 그때 다시 만들어야 한다.
- **그림을 텍스트로 부풀리지 않는다.** base64는 33% 커지고, 그 전부가 파싱 대상이 된다.

### 2.3 형식은 JSON — XML이 아니다

*"프로젝트 포맷은 보통 XML 쓰잖아. 툰붐 하모니도 그렇고."* 맞다. 하모니의
`.xstage`는 XML이고 프리미어 `.prproj`는 gzip된 XML, AE도 `.aepx`가 XML판이다. 다만
규칙은 아니다 — AE 기본 `.aep`와 포토샵은 바이너리고, 요즘 것들은 바이너리나 DB다.

이 앱에서 JSON을 고르는 이유는 취향이 아니라 **이미 전부 JSON이라서**다.

- 엔진과 화면이 JSON 한 줄씩 주고받는다(RPC 프로토콜)
- **저장할 레이어 트리는 엔진이 준 JSON 그대로**다. XML로 쓰면 내보낼 때 변환하고
  읽을 때 되돌리는 층이 생기고, 그 층은 언젠가 원본과 어긋난다
- `OpsState`도 `presets.json`도 이미 JSON이고 검증기도 그 idiom으로 짜여 있다
- 프런트는 `JSON.parse`가 내장이라 라이브러리가 필요 없다

XML로 얻는 것(읽기 쉽다, diff가 된다)은 JSON도 똑같이 준다. **스튜디오 파이프라인
도구가 이 파일을 읽어야 한다면** 그때 다시 볼 것 — 그건 형식이 아니라 요구사항이 바뀌는
경우다.

### 2.4 `project.json`

```jsonc
{
  "version": 1,
  "preset": { /* 저장 시점에 선택돼 있던 Preset 전체 */ },
  "files": [
    {
      "path": "/Volumes/<납품볼륨>/<컷폴더>/<파일>.psd",
      "mtime": 1754800000,        // 저장 시점 디스크 수정시각
      "tree": [ /* TreeNode[] — open_psd가 준 그대로 */ ],
      "matchedIds": [12, 44],     // 프리셋 매칭 결과
      "ops": { /* OpsState 전체 */ },
      "previewKey": "…",          // previewCacheKey가 만든 문자열
      "previewFile": "a1b2c3.png" // previews/ 안의 이름
    }
  ]
}
```

**트리를 담는 것이 "전부 그대로 뜬다"의 핵심이다.** 레이어 패널은 `FileEntry.tree`만
있으면 그려진다. 이 앱에는 세션 없이 트리만으로 도는 경로가 이미 있다 — 자동 병합이
그렇고, 그 이유가 `rpc.py`에 적혀 있다: *"세션을 요구하면 그것이 축출됐을 때 700MB짜리
파일을 통째로 다시 읽어야 한다 — 버튼 한 번에 3.4초다."* 같은 논리가 여기 그대로
적용된다.

## 3. 여는 순서

1. `project.json`을 읽어 파일 목록·트리·`OpsState`·매칭 결과·프리셋을 세운다.
   **엔진에 아무것도 안 간다.**
2. 파일마다 디스크의 수정시각을 확인한다. 다르면 **그 파일의 작업과 미리보기를 버리고**
   목록에 "파일이 바뀌었습니다"로 표시한다(4절).
3. 살아남은 파일의 PNG를 `PreviewCache`에 넣는다. 키는 저장된 것을 쓰지 않고 **복원한
   상태로 다시 계산해서 대조한다**(5절).
4. 그 뒤 배경에서 지금처럼 세션을 채운다. 새로 그리거나 내보낼 때 필요한 것이고,
   그동안에도 화면은 이미 다 떠 있다.

1~3은 디스크 읽기뿐이라 즉시다. **100장 6분을 기다렸다 시작하던 것이 열자마자
시작으로 바뀐다.**

## 4. 파일이 바뀌었으면 버린다

아티스트가 고른 규칙이다. 저장된 것은 전부 **레이어 id**로 되어 있고 그 id는 트리를
훑는 순서에서 나오므로, PSD가 바뀌면 id가 밀려 "라인 지정"이 엉뚱한 레이어를 가리킬 수
있다 — 그것도 조용히. 오늘 배치에서 막은 것과 같은 실패다(`batch.py`의
`_add_manual_lines`).

판정은 **경로 + 수정시각**이고, 이 앱이 이미 쓰는 규약이다(`previewCache.ts:115`의
주석 참고 — 세션 id를 쓰다 캐시가 무력화된 이력이 있다).

버린 파일은 목록에 남되 작업 없이 열린다. 조용히 지우면 아티스트는 자기가 한 지정이
왜 없는지 알 수 없다.

## 5. 유효성 판정을 새로 만들지 않는다

미리보기가 아직 맞는 그림인지는 **기존 캐시 키가 이미 판정한다**. 키에는 경로·수정시각·
문서보기 여부·보이는 레이어·라인색·색 통일 대상·경계선 설정·색 원본 지정·체크 목록이
전부 들어 있다(`previewCacheKey`).

그래서 복원은 이렇게 된다: `OpsState`를 그대로 되살리면 키가 그대로 다시 계산되고,
그 키로 PNG를 캐시에 넣으면 `needsPrefetch`가 "만들 것 없음"으로 판정해 **준비 큐가
아무것도 다시 그리지 않는다.**

**저장된 `previewKey`는 믿지 않고 대조에만 쓴다.** 복원한 상태로 계산한 키가 저장된
키와 다르면 그 PNG는 버린다 — 다르다는 것은 저장과 복원 사이에 규칙이 바뀌었다는
뜻이고(앱 업데이트로 키 구성이 늘어나는 일은 실제로 있었다), 그때 옛 그림을 붙이면
아티스트는 지금 설정과 다른 그림을 보면서 확인했다고 믿게 된다.

## 6. 저장은 수동

아티스트가 정했다. **저장하지 않으면 앱은 오늘과 똑같이 동작한다.**

- `⌘S` 저장 / `⌘⇧S` 다른 이름으로 저장. 저장한 적 없으면 `⌘S`가 위치를 묻는다
- 저장하는 순간 그 시점 화면의 미리보기 PNG가 `previews/`로 복사된다. 엔진이 이미
  PNG를 파일로 쓰므로(`render_preview`의 `pngPath`) 다시 인코딩할 것이 없다
- **종료 확인창·자동 저장·자동 복구는 만들지 않는다.** 아티스트가 "저장 안 하면
  기존대로 가면 돼"라고 명시했다

## 7. 배선 — 빠뜨리면 조용히 망가지는 자리

- **`matchedIds`를 같이 저장한다.** 없으면 복원 후 `lineColorIdsFor`가 null을 주고
  ("전부 건다"는 뜻) 캐시 키가 달라져 전부 다시 그린다. 복원의 목적이 무너진다.
- **트리와 `mtime`은 한 몸이다.** 트리만 믿고 mtime 확인을 건너뛰면 바뀐 파일의 옛
  트리로 화면을 그리게 된다.
- **프리셋도 프로젝트에 담는다.** 프리셋 목록은 앱 데이터에 따로 사는데, 그 사이 순서나
  내용이 바뀌면 복원한 작업과 어긋난다 — 오늘 겪은 사고가 정확히 그것이다
  (`presets.json`을 갈아끼우자 배치 기본값이 조용히 바뀌었다).
- **`previews/`의 이름은 키 해시로 짓는다.** 파일명으로 지으면 납품 파일명이 디스크에
  남는다 — 기밀이다.
- **배치 패널의 프리셋 선택은 이 프로젝트의 프리셋을 따라야 한다.** 지금은 자기
  드롭다운의 첫 번째를 쓴다.

## 8. 안 하는 것

- **PSD 픽셀을 담지 않는다.** 프로젝트는 참조와 결정과 미리 만들어둔 그림이다.
- **여러 상태의 미리보기를 담지 않는다.** 저장 시점 화면의 한 장씩만이다. 토글 조합마다
  담으면 폴더가 몇 기가가 된다.
- **되돌리기 이력을 담지 않는다.** `ops`는 담지만 undo 스택은 세션 것이다.
- **자동 저장·복구를 만들지 않는다**(6절).
